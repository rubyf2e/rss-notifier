### Auth / Stale Session

特別處理 Frontend **stale auth session**。

`localStorage` 不得再被視為可信的登入狀態來源，只能作為 session restore/cache。

重新整理受保護頁面時：

1. restore localStorage
2. 使用正式 Backend API 驗證目前 session / user 是否仍有效
3. Backend 判定不存在、未授權或 session 無效：
   - 清除 stale auth/session/user
   - 更新 reactive auth state
   - 導向 login
4. 不得因 localStorage 舊資料繼續顯示受保護頁面
5. 避免：
   - redirect loop
   - 重複 session validation
   - auth state 與 localStorage 不同步
   - 驗證尚未完成就錯誤渲染受保護內容

優先使用目前 Backend 已存在且 Postman 有定義的 API。

**不要因 stale session 問題修改 Backend 或新增 Backend endpoint。**

如果現有 API 無法完整驗證 session，依目前 contract 做最小可行整合，並在完成報告指出限制。

### API Error Handling

Frontend **不得自行定義 API 錯誤訊息**。

所有 Backend API error：

- 優先使用 Backend response 的 `message`
- Frontend 只負責取得、保存、顯示
- 不把 HTTP status 自行轉成另一段使用者訊息
- 不建立例如：
  - `if (status === 401) error = '登入已過期'`
  - `if (status === 404) error = '找不到資料'`
  - `errorMessages = {...}`
  之類的 Frontend API error mapping

可以根據 HTTP status 做**控制流程**，例如：

- 401 → 清除 auth + redirect login

但顯示給使用者的 API error message 必須使用 Backend `message`。

若 Backend error response 的 `message` 可能是 string 或 string array，依目前 Backend 實際 contract 正確處理，不自行改寫內容。

Network error / request 根本沒有取得 Backend response 的情況，沿用目前 Frontend 的既有 generic handling；不要冒充 Backend message。
